# Problems 筆記結構

依既有專案格式調整；省略不適用的章節，不保留空白占位文字。

```markdown
# <可搜尋的問題或觀念標題>

- **紀錄代號**：<分類目錄名稱>-<NNN>；例如 `typescript-typeorm-001`
- **分類**：<既有分類名稱>
- **子主題**：<選填；工具、框架或概念>
- **首次討論日期**：<YYYY-MM-DD>
- **最後更新日期**：<YYYY-MM-DD；首次建立時與首次討論日期相同>
- **討論來源**：<目前 task 或 task 標題；預設不寫內部 UUID>
- **相關檔案**：`<path>`、`<path>`
- **狀態**：<建議方案；尚未實作／已實作；尚未驗證／已驗證／部分完成>
- **關鍵字**：`<error>`、`<API>`、<concept>

## 1. 討論問題

說明使用者想釐清或解決什麼。若有連續追問，整合成同一條清楚的問題脈絡。

## 2. 問題現象與上下文

記錄實際錯誤、行為、限制或設計背景。精確錯誤訊息使用 `text` code block。

## 3. 原因與關鍵觀念

區分已確認的根因、合理推論與尚待驗證事項。解釋容易混淆的概念，不只列出答案。

## 4. 實際建議

按執行順序列出討論中最後採用的建議。必要時附最小程式碼或指令，並說明預期效果與風險。

## 5. 採用與驗證結果

| 建議 | 採用狀態 | 證據或結果 |
|---|---|---|
| <建議> | 已採用／部分採用／未採用／待處理 | <檔案、測試、輸出或「尚無驗證證據」> |

若整場討論只有建議，明寫「本次未修改程式碼，尚無實作或驗證結果」。

## 6. 容易混淆的觀念

- <相似概念的差異>
- <先前建議被後續討論修正之處>

## 7. 後續行動

- [ ] <仍需實作或驗證的項目>
- [ ] <需要重新檢查的相依工作>

## 8. 複習檢查清單

- [ ] 能否從錯誤訊息辨認問題發生階段？
- [ ] 建議是否符合目前專案設定與版本？
- [ ] 文件狀態是否有實際證據支持？

## 9. 更新紀錄

| 日期 | 更新內容 | 驗證狀態 |
|---|---|---|
| <YYYY-MM-DD> | <首次整理或後續補充內容> | <尚未驗證／已驗證／部分完成> |
```

## 選用原則

- 教學型問題：保留「關鍵觀念」「容易混淆」「複習檢查清單」。
- 錯誤排查：保留精確錯誤、排查順序、根因、修正與驗證。
- 設計討論：記錄設計限制、選項比較、最終建議與尚未決定事項。
- 開發順序：記錄前置條件、建議順序、各步完成證據與阻塞點。
- 已有同主題筆記：更新最後更新日期、狀態、驗證結果與更新紀錄，不建立同義檔案。

## 寫作品質檢查

- 每個「已完成」「已解決」「已驗證」都有可指出的證據。
- 最終建議沒有保留已被後續討論推翻的寫法。
- 相關檔案只列實際存在或討論明確提及的路徑。
- 新筆記使用 `NNN-<topic>.md`，且紀錄代號為對應的 `<category>-NNN`。
- 同一分類的三位數流水號沒有重複；既有主題仍更新原檔，不另建代號版本。
- 首次討論日期不因後續更新而改寫；最後更新日期與更新紀錄反映最近一次討論。
- 檔名、H1 與索引文字描述同一主題。
- 筆記能在離開原 task 後獨立理解。
