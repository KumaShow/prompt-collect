# 後端起手流程 SOP — 從 PRD 到可執行的 API

> 定位：通用流程筆記，跨專案可重用。
> 讀者：有前端經驗、正在補後端流程的開發者。
> 建立：2026-08-03

---

## 〇、為什麼後端的順序和前端不一樣

前端接到需求的起點是**設計稿**：畫面長什麼樣 → 拆元件 → 串 API。
後端接到需求的起點是**資料**：資料長什麼樣 → 誰能動它 → 用什麼介面暴露出去。

原因是**修改成本不對稱**：

| 決策層級 | 改動成本 | 說明 |
|---|---|---|
| 資料模型（表、欄位、關聯） | 極高 | 已上線的資料要寫 migration 搬移，錯的資料可能救不回來；API 和前端全部連帶重寫 |
| API 契約（路由、request/response 形狀） | 中 | 前端要跟著改，但改完就好；可用版本號或相容欄位緩衝 |
| 內部實作（怎麼寫 service、怎麼查詢） | 低 | 只要契約不變，隨時可以重寫、可以優化 |

所以流程的原則是：**成本越高的決策，越早想清楚、越晚寫死。**
先在紙上（文件裡）改十次資料模型，比在資料庫裡改一次便宜。

前端的對照經驗：這就像「元件 props 介面」vs「元件內部實作」。props 改了所有使用它的地方都要改，內部實作改了沒人知道。資料模型就是後端最外層的 props，而且是**有記憶的** props。

## 一、流程總覽

```txt
1. 讀需求：抽出 名詞 / 動詞 / 規則
        ↓
2. 列模糊點與假設 → 回頭問 PM（或自己拍定並記錄）
        ↓
3. 資料模型設計  ← 地基，花最多時間思考的地方
        ↓
4. API 契約設計  ← 前後端的分界線，定好雙方可平行開工
        ↓
5. 專案架構分層  ← 決定程式碼放哪裡
        ↓
6. Walking Skeleton：讓最短一條路徑從頭到尾跑通
        ↓
7. 垂直切片實作：一次做完一個功能（DB → API → 驗證）
        ↓
8. 邊做邊驗證：REST client / 自動化測試
        ↓
9. 留下文件：README、決策記錄、API spec
```

第 3、4 步是「設計」，第 6-8 步是「實作」。**新手最常犯的錯是跳過 3、4 直接寫程式**，寫到一半發現資料表要改，於是整個重來。

## 二、Step 1：讀需求 — 名詞 / 動詞 / 規則三分法

不要從第一頁讀到最後一頁。拿三支不同顏色的筆（或三個清單），把 PRD 拆成三堆：

### 名詞 → 未來的資料表 / 實體

找 PRD 裡反覆出現的「東西」。它們會變成表。

判斷是不是實體的問法：
- 它需要被單獨存起來、被查詢、被列表嗎？→ 是實體
- 它只是另一個實體的一個屬性嗎？→ 是欄位

> 本專案範例：使用者、類別、Prompt/Skill、收藏 → 四個實體。
> 「標籤」是個有趣的邊界案例：它可以是 SkillItem 的一個欄位（字串陣列），也可以是獨立的表。這就是需要**設計判斷**的地方，PRD 不會幫你決定。

### 動詞 → 未來的 API 端點

找「誰可以做什麼」。每個動詞對應一支 API。

> 本專案範例：登入、登出、新增類別、編輯類別、刪除類別、新增資料、瀏覽列表、搜尋、篩選、看詳情、收藏、取消收藏、看我的收藏。

把動詞列成表，馬上就能對照 PRD 的功能規格檢查有沒有漏。

### 規則 → 未來的驗證、權限、約束

找「不能」、「必須」、「至少」、「重複」這類字眼。這些會變成三種東西：

| 規則類型 | 實作位置 | 例子 |
|---|---|---|
| 格式驗證 | 進入點的 schema 驗證（zod） | 標題不能空白、email 要合法格式 |
| 業務規則 | service 層 | 有資料的類別不能刪除 |
| 資料完整性 | 資料庫約束 | 同一人不能重複收藏同一筆（unique constraint） |

**重點觀念**：同一條規則可能需要在多層都擋。例如「不能重複收藏」，前端要讓按鈕變成已收藏狀態（UX）、後端 service 要檢查（清楚的錯誤訊息）、資料庫要有 unique 約束（最後防線，防併發）。前端只做第一層，後端要做後兩層。

### 產出物

一張三欄表格。這張表就是你「翻譯」需求的證據，之後 review 資料模型和 API 時都會回來對照它。

## 三、Step 2：列出模糊點與假設

PRD 永遠不會寫完所有細節。這一步的價值是**在寫程式前就發現坑**，而不是寫到一半才問。

### 找模糊點的固定問法

對每個實體問：
- 這筆資料被刪除時，關聯的資料怎麼辦？（連帶刪除 / 阻擋 / 設為 null）
- 這個欄位可以是空的嗎？可以重複嗎？有長度上限嗎？
- 誰可以讀？誰可以寫？讀到的內容因角色而不同嗎？

對每個列表 API 問：
- 要分頁嗎？預設幾筆？（**沒分頁的列表 API 是後端最常見的隱形炸彈**）
- 預設排序是什麼？使用者可以改嗎？
- 空結果是錯誤還是正常狀態？

對每個角色問：
- 這個角色能做的事，有沒有「看起來合理但 PRD 沒說」的？
  （例：管理者可以收藏嗎？PRD 只說會員可以收藏，那管理者呢？）

### 產出物：假設清單

問得到 PM 就問。問不到（或像本專案是自己一人開發）就**明確寫下假設並記錄理由**，這份紀錄之後就是你的「設計決策說明」。

```md
## 假設清單
- A-01 列表 API 一律分頁，預設 20 筆。理由：資料量成長後不改會出事，成本現在最低。
- A-02 管理者也可以收藏。理由：管理者本身也是使用者，且不增加額外權限複雜度。
- A-03 刪除 SkillItem 時連帶刪除相關收藏。理由：收藏指向不存在的資料沒有意義。
```

## 四、Step 3：資料模型設計（地基）

這是後端最需要「想清楚才動手」的一步。順序如下：

### 3-1 確認實體清單

從 Step 1 的名詞來。每個實體問一次：「它可以被獨立查詢嗎？」如果不行，它應該是別人的欄位。

### 3-2 決定關聯（最容易錯的地方）

對每兩個實體問：**一個 A 對應幾個 B？一個 B 對應幾個 A？**

| 答案 | 關聯類型 | 實作方式 |
|---|---|---|
| 一個 A 一個 B、一個 B 一個 A | 1:1 | 其中一邊放 foreign key + unique |
| 一個 A 多個 B、一個 B 一個 A | 1:N | **多的那邊**放 foreign key |
| 一個 A 多個 B、一個 B 多個 A | M:N | 需要中間表（join table） |

**1:N 的 FK 一定放在「多」的那邊**——因為一個欄位只能放一個值。一篇文章有多個留言，FK 放在留言表指向文章，而不是文章表存留言清單。

**M:N 需要中間表**——當中間表本身還需要額外欄位（例如「收藏時間」）時，它就不只是 join table，而是一個真正的實體。

### 3-3 逐欄位定稿

每個欄位要決定五件事：

1. **型別**：字串長度多少？金額用 decimal 不要用 float。時間用 timestamptz。
2. **可否為 null**：null 代表「不知道」，不是「空的」。空字串和 null 不一樣，選一種並保持一致。
3. **預設值**：由資料庫給還是程式給？
4. **唯一性**：需不需要 unique？複合 unique？
5. **索引**：這個欄位會被 WHERE / JOIN / ORDER BY 用到嗎？

### 3-4 從查詢反推索引（但別過早建）

問自己：「這張表未來會被怎麼查？」
- 會用 email 找使用者 → email 要索引（而且要 unique）
- 會用 categoryId 篩選資料 → FK 通常需要索引（**PostgreSQL 不會自動為 FK 建索引**）
- 會用關鍵字模糊搜尋 → 一般索引對 `LIKE '%xxx%'` 無效，需要別的方案（MVP 階段可以先接受慢，但要知道為什麼慢）

**但索引不是免費的，也不該一開始就全建上：**

- 佔磁碟空間（GIN / GiST 這類尤其大）
- 每次 INSERT / UPDATE / DELETE 都要同步維護 → **寫入變慢**
- **小表上零效益**：查詢規劃器會判斷「讀索引再回表」比整張表掃過去更貴，於是**根本不使用你建的索引**

#### 關鍵區分：兩種索引的目的不同

| 類型 | 例子 | 何時建 |
|---|---|---|
| **約束性索引** | PK、`UNIQUE(email)`、複合唯一約束 | **一開始就要**。目的是**保證正確性**，不是加速查詢——沒有它就防不了重複資料 |
| **效能性索引** | 排序欄位、FK、GIN / 全文檢索 | **測量到問題才建**。純優化，資料量不到就是純成本 |

#### 判斷準則：先測量再優化

用 `EXPLAIN ANALYZE` 看到 Seq Scan **且執行時間真的有問題**，才加索引。

粗略量級感：幾千筆以上開始有感，幾萬筆以上不加會痛。幾十筆的表加效能索引沒有意義。

> **為什麼索引可以晚做？** 因為 `CREATE INDEX` 是**所有技術決策裡最可逆的一種**——一行 SQL、不改程式碼、不用資料搬移、隨時可 `DROP`。回到本文件開頭的成本不對稱原則：**可逆的決定就該晚做，不可逆的才要早想。**
>
> 這和資料模型形成對照：欄位型別選錯要 migration 搬資料（貴，要早想）；索引沒建（便宜，可以晚做）。同一份 schema 裡，不同決策的「該不該現在決定」是不一樣的。

### 3-5 決定刪除行為

每個 FK 都要決定 `ON DELETE` 行為：

| 行為 | 意義 | 適用時機 |
|---|---|---|
| `CASCADE` | 父資料刪除，子資料一起刪 | 子資料離開父資料就沒意義（收藏 → 被收藏的項目） |
| `RESTRICT` / `NO ACTION` | 有子資料就不准刪父資料 | 要保護資料完整性（有商品的分類不准刪） |
| `SET NULL` | 父資料刪除，子資料的 FK 設為 null | 關聯是選填的 |

**不決定不代表沒有行為**——ORM 會給你一個預設值，那個預設值可能不是你要的。

### 產出物

ER 圖 + 欄位定稿表 + 決策理由。**寫完這份才開始寫 Entity 程式碼。**

### migration vs synchronize

ORM 通常提供兩種建表方式：

- `synchronize: true`：啟動時自動比對 Entity 和資料庫，自動改 schema。方便，但它可能**為了對齊而刪掉欄位或整張表**，且沒有紀錄、無法回溯。只適合本機隨時可以砍掉重建的資料庫。
- migration：每次 schema 變更產生一個帶時間戳的檔案，進 git，可以 run 也可以 revert。是**團隊協作和正式環境的唯一選擇**。

正式環境永遠用 migration。學習階段建議一開始就用 migration，因為它會強迫你意識到「schema 的每次改動都是一個事件」。

## 五、Step 4：API 契約設計

契約定好，前後端就可以平行開工——這是前端出身的人最容易理解的價值：**你曾經多希望後端早點給你 API 文件**。

### 要決定的項目

**1. 路由與動詞（RESTful 慣例）**

```txt
GET    /skills          列表
GET    /skills/:id      單筆
POST   /skills          新增
PATCH  /skills/:id      部分更新
PUT    /skills/:id      整筆取代
DELETE /skills/:id      刪除
```

- 路徑用**複數名詞**，不要放動詞（`/getSkills` ❌）
- 動作放在 HTTP method，不是路徑
- 巢狀最多兩層（`/users/:id/favorites` 可以，再深就難維護）
- `PATCH` 是部分更新，`PUT` 是整筆取代，兩者語意不同，選了要一致

**2. 統一回應格式**

決定要不要包一層信封：

```jsonc
// 方案 A：直接回資料（簡潔，靠 HTTP status 表達成功/失敗）
{ "id": 1, "title": "..." }

// 方案 B：包信封（一致，前端可統一處理）
{ "status": "success", "data": { "id": 1, "title": "..." } }
```

兩種都可以，**重點是全站一致**。前端的 interceptor 只想寫一次拆解邏輯。

**3. 統一錯誤格式與狀態碼**

| 狀態碼 | 意義 | 常見場景 |
|---|---|---|
| 400 | 請求格式錯誤 | 必填欄位空白、型別錯誤 |
| 401 | 未認證 | 沒帶 token、token 過期、帳密錯誤 |
| 403 | 已認證但無權限 | 會員想打管理者 API |
| 404 | 找不到資源 | id 不存在 |
| 409 | 狀態衝突 | 重複建立、重複收藏 |
| 422 | 語意錯誤（選用） | 格式對但業務上不合法 |
| 500 | 伺服器錯誤 | 未預期的例外（兜底） |

**401 vs 403 的分野**：401 是「我不知道你是誰」，403 是「我知道你是誰，但你不能做這件事」。

錯誤回應也要統一形狀，並且**帶機器可讀的錯誤碼**，讓前端能針對特定錯誤做特定處理，而不是比對中文訊息字串：

```jsonc
{
  "status": "error",
  "code": "DUPLICATE_FAVORITE",   // 前端判斷用
  "message": "已經收藏過此項目"     // 給人看的
}
```

**4. 權限標註**

每個端點標清楚：公開 / 需登入 / 需特定角色。這張表就是之後掛 middleware 的依據。

**5. 列表端點的參數慣例**

分頁、排序、篩選的參數名稱全站統一（`page`/`limit`/`sort`/`keyword`），不要一支用 `page` 另一支用 `offset`。

### 安全原則：response 是白名單，不是黑名單

**永遠明確列出要回傳哪些欄位，而不是「回傳整個物件再刪掉敏感的」。**

```ts
// ❌ 危險：未來新增敏感欄位時會自動洩漏
const { passwordHash, ...safe } = user
return safe

// ✅ 安全：新增欄位不會意外外洩
return { id: user.id, name: user.name, email: user.email, role: user.role }
```

這是後端最常見的資安事故來源之一：把 ORM 撈出來的整個 entity 直接 `res.json()`，密碼雜湊、內部備註、其他人的資料就一起送出去了。

### 產出物

API spec 表格或 OpenAPI 文件。至少要包含：路由、method、權限、request 形狀、response 形狀、可能的錯誤。

## 六、Step 5：專案架構分層

典型的四層，一個請求由外往內走：

```txt
route       路由定義：這個 URL 交給誰處理，掛哪些 middleware
   ↓
controller  處理 HTTP：解析 request、驗證輸入格式、呼叫 service、組裝 response
   ↓
service     業務邏輯：規則判斷、跨資料表的協調、交易控制
   ↓
repository  資料存取：查詢與寫入資料庫
```

**為什麼要分層？**

1. **可測試**：service 不碰 req/res，可以直接餵參數測，不用啟動 HTTP server。
2. **可替換**：repository 是介面，底層換成別的資料來源時，service 完全不用改。
3. **不重複**：多支 API 需要同一段業務邏輯時，它有一個明確的家。

**分層的規矩**：
- controller **不寫業務邏輯**——它只做 HTTP 的翻譯工作
- service **不認識 req/res**——它不知道自己被 HTTP 呼叫還是被 CLI 呼叫
- 資料庫查詢**不出現在 controller**

**什麼時候可以偷懶？** 專案很小、一支 API 只是單純的 CRUD 時，controller 直接呼叫 repository 是可接受的。但一旦出現「跨表操作」或「多支 API 共用邏輯」，就該把 service 抽出來。判斷標準：**開始複製貼上的時候，就是該分層的時候。**

## 七、Step 6：Walking Skeleton（先跑通最短路徑）

不要一次做完所有 API。先讓**一條最短但完整的路徑**從頭到尾通：

```txt
HTTP 請求 → route → controller → service → repository → 真實資料庫 → 回傳真實資料
```

例如：一支 `GET /categories` 讀出資料庫裡真的存在的類別。

**為什麼？** 這條路徑上每個環節都可能出問題——連線字串錯、ORM 設定錯、TypeScript 編譯設定錯、Docker 網路錯。一次只驗證一個環節，比全部寫完再一起 debug 容易十倍。

這個技巧的名字是 walking skeleton（會走路的骨架）或 vertical slice（垂直切片）：先做一根從天到地的細柱子，再往兩邊長。

---

## 八、Step 7：垂直切片實作

骨架通了以後，**一次做完一個功能**，而不是「先做完所有 entity、再做完所有 controller」。

每個切片包含：資料層 → 業務邏輯 → API → 驗證通過。做完一個才開始下一個。

### 實作順序照「風險」排，不照「難易」排

先做**最不確定、最核心、失敗代價最大**的部分：

1. 有技術不確定性的（第一次用的套件、沒做過的機制）
2. 其他功能都依賴的（認證與權限——所有 API 都要靠它）
3. 純 CRUD（模式重複，做過一個其他就是套用）
4. 加分項（有時間才做）

原因：不確定的東西越早做，越早知道要不要換方案。如果把最難的留到最後，發現做不出來時已經沒有時間調整。

## 九、Step 8：邊做邊驗證

**後端沒有畫面，REST client 就是你的畫面。**

前端寫完 component 可以馬上在瀏覽器看到；後端寫完 API 必須主動去打它。工具選擇：

| 工具 | 特點 |
|---|---|
| VS Code REST Client 外掛（`.http` 檔） | 純文字、**可以進 git**、變成團隊活文件。推薦 |
| Postman / Insomnia | GUI 友善，適合探索與分享 collection |
| `curl` | 隨手可用，適合快速確認 |
| 自動化測試（supertest + vitest） | 可重複執行，改壞會被抓到 |

### `.http` 檔的價值

它同時是「測試腳本」和「API 使用範例」。新人接手時，照著 `.http` 檔打一輪就懂整套 API 怎麼用。

```http
@baseUrl = http://localhost:3000
@token = {{login.response.body.data.token}}

### 登入
# @name login
POST {{baseUrl}}/auth/login
Content-Type: application/json

{ "email": "admin@example.com", "password": "password" }

### 取得目前使用者
GET {{baseUrl}}/auth/me
Authorization: Bearer {{token}}
```

### 每支 API 至少驗證四種情境

1. **正常路徑**：正確輸入 → 預期結果
2. **格式錯誤**：缺欄位、型別錯 → 400
3. **權限錯誤**：不帶 token → 401；帶錯角色的 token → 403
4. **邊界情境**：不存在的 id → 404；重複建立 → 409

新手只測第 1 種，然後 demo 時被第 3 種炸掉。

## 十一、前端 → 後端的思維切換表

| 面向 | 前端習慣 | 後端要換的腦袋 |
|---|---|---|
| 起點 | 設計稿 | 資料模型 |
| 狀態 | 在記憶體，重整就沒了 | 要持久化，寫錯了會一直在那裡 |
| 使用者數 | 一個（當下這個人） | 同時很多人 → 要想併發、鎖、交易 |
| 出錯代價 | 重整就好 | 髒資料留在 DB，可能要寫腳本修 |
| API | 別人給你的契約 | **你定的契約，別人依賴它** → 改動要考慮相容 |
| 驗證目的 | UX（早點告訴使用者） | 安全（前端驗證可以被繞過，**後端是唯一防線**） |
| 「隱藏」的意義 | 隱藏按鈕 = 使用者不能做 | 隱藏只是視覺；**沒擋 API 就等於沒擋** |
| 效能瓶頸 | 首屏、bundle size、重繪 | 資料庫查詢次數、N+1、缺索引 |
| 除錯 | DevTools 看得到一切 | 只有 log 和測試，要主動製造可觀測性 |

**最重要的一條**：前端的驗證是為了體驗，後端的驗證是為了安全。任何人都可以用 curl 直接打你的 API，繞過你所有前端邏輯。**後端必須假設所有進來的請求都是惡意的。**

## 十二、新手常見坑 Top 10

1. **只有前端擋權限，後端沒擋**。前端藏掉的按鈕，用 curl 一樣打得到。
2. **回傳整個 entity**，把 `passwordHash` 一起送出去。用白名單挑欄位。
3. **在正式資料庫用 `synchronize: true`**。它會為了對齊 schema 而刪資料。
4. **沒有統一錯誤處理**，每個 handler 各寫一套 try-catch，錯誤格式全站不一致。
5. **列表 API 沒有分頁**。資料一多就整個拖垮。
6. **驗證散落在 handler 裡**用 if 硬檢查。用 schema 驗證（zod）集中管理，並讓型別跟著出來。
7. **N+1 查詢**：撈 100 筆列表，再在迴圈裡逐筆查關聯 → 101 次查詢。要用 join 或 relations 一次撈完。
8. **環境變數沒驗證就用**。少一個變數，等到某支 API 被呼叫才炸，而且錯誤訊息看不出原因。啟動時就要驗證並中止。
9. **把「防重複」只寫在程式碼裡**，沒有資料庫 unique 約束。兩個請求同時進來就會產生兩筆。
10. **密碼相關的錯誤訊息太詳細**。「此帳號不存在」洩漏了哪些帳號存在，讓攻擊者可以列舉使用者。統一回「帳號或密碼錯誤」。
